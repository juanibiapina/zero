---
title: GitHub Actions without an API key
description: Let a GitHub Actions workflow read ZeroVault secrets by trusting the repository instead of storing a key.
---

Your workflow can read secrets without a `ZERO_API_KEY` in GitHub. GitHub signs
a token that says which repository and job is running. You tell Zero to trust
that repository, and the job swaps the token for access that expires after 15
minutes.

An API key in GitHub is the easiest one to lose: it never expires, it opens
every project in your organization, any workflow in the repository can read it,
and you have to rotate it by hand.

## Set it up

Trust the repository once, from a terminal where `zero` is already signed in:

```bash
zero ci trust add --repo octo-org/octo-repo
```

Then let the job ask GitHub for its token, and delete the secret:

```yaml
permissions:
  id-token: write        # without this, the job has no identity

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx @zeroapps/cli@0.5.0 vault secrets download -p demo -e production -f env -o .env
```

There is no `ZERO_API_KEY` and no `secrets.*` line. Run `zero whoami` in the job
and it prints `Credential: github actions`.

Wait a minute after `zero ci trust add` before the first run. Until then it is
refused.

## Private repositories

`zero ci trust add` reads the repository's numeric ids from GitHub's public API,
which cannot see private repositories. Set a `GITHUB_TOKEN` that can read it, or
pass the ids yourself:

```bash
zero ci trust add --repo octo-org/private-repo --owner-id 65 --repo-id 74
```

A refused run prints both ids too, so you can copy them from the failure.

## Trust less than the whole repository

A trusted workflow reads every secret in your organization. Limit it to the runs
that need to:

```bash
zero ci trust add --repo octo-org/octo-repo --ref refs/heads/main
zero ci trust add --repo octo-org/octo-repo --environment production
```

`--ref` must match the run's git ref. `--environment` must match the job's
`environment:`.

## Pull requests are refused

Three triggers are refused unless you allow them, because they run as your
repository but on code from outside it:

| Trigger | Why |
|---|---|
| `pull_request` | Runs code from a branch nobody has reviewed yet |
| `pull_request_target` | Runs with your secrets on a pull request from a fork |
| `workflow_run` | Runs with your secrets after another workflow, including one a pull request started |

```bash
zero ci trust add --repo octo-org/octo-repo --allow-event pull_request
```

Allowing one does not allow the others.

Be careful with `pull_request_target` and `workflow_run` if your workflows check
out pull request code. Anyone who can open a pull request can then run their own
code in a job that holds your secrets.

`--ref` does not help here. A `pull_request_target` run reports
`ref: refs/heads/main`, so a main-only rule still lets it through. Only the
trigger rule stops it.

## Managing trust

```bash
zero ci trust list           # id, repository, and any limits
zero ci trust rm <id>        # stop trusting it
```

Removing trust stops the next run. Access a job already has keeps working until
it expires, so at most 15 minutes.

## Where you still need a key

- **Other CI.** GitLab, CircleCI and Buildkite sign similar tokens, but Zero
  only accepts GitHub's for now.
- **Servers and containers.** Nothing signs a token for them. Use a key, one per
  host if you can.
- **Smaller than an organization.** Trust cannot be limited to one project. A
  trusted workflow reads everything in the organization, same as a key.
