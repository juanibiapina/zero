# Todo sync libraries: fit for the existing app

**2026-09-25 — Decision:** **Use TinyBase** for the signed-in local-replica refactor. The user excluded RxDB and chose TinyBase after comparing Jazz 2 and Rocicorp Zero. TinyBase supplies Expo persistence, per-cell convergence and a Cloudflare DO synchronizer without a paid mobile-storage license. Project/Task/After integrity, authenticated routing, and existing web/server writers must be integrated into **one** todo authority, not dual-written across stores. Rocicorp Zero rejects offline writes; Jazz 2 would require a separate sync backend and its Expo integration is alpha; LiveStore requires a larger event-sourced migration. Keep those comparisons below as rationale, not parallel implementation tasks. An [archived isolated Worker and Android proof](https://github.com/juanibiapina/zero/blob/a7c78c39e8b82e1340bfc6956940a9d9fdc167d3/spikes/tinybase/README.md) verifies transport, SQLite restart durability, and a REST writer sharing the DO store. It also proves that direct WebSocket sync can bypass REST validation and propagate a Task referencing a nonexistent Project.

**2026-09-26 — Outcome:** the integration and cutover completed. Per-account `TaskDO` is now the unconditional todo authority. Raw invalid relationships remain visible through the recovery projection; the legacy `UserDO` todo tables are inert recovery data, not a second authority.

## Implementation gate: direct-sync validation

**Correction after testing:** TinyBase 10.0.1 does have a [middleware interface](https://tinybase.org/api/middleware/interfaces/middleware/middleware/methods/configuration/addwillapplychangescallback/) that intercepts `applyMergeableChanges`; the initial inspection of `WsServerDurableObject.onMessage` missed it. But this is a store write hook, not a pre-relay admission gate. The reproducible [two-client WebSocket experiment](https://github.com/juanibiapina/zero/blob/a7c78c39e8b82e1340bfc6956940a9d9fdc167d3/spikes/tinybase/scripts/middleware-proof.ts) applied `createMiddleware(serverStore).addWillApplyChangesCallback(() => undefined)` to an invalid Task. The server's visible row stayed empty **but its in-memory merge hash changed**; both an already-connected client and a newly connected client received the invalid row while the original peers remained connected. After every invalid peer disconnected, a later client loaded an empty store. A thrown middleware error rolled back the hash in a direct local merge, but throwing during the WebSocket experiment crashed the Node server. This is not a safe rejection/acknowledgment mechanism.

`setTablesSchema` validates cell shapes, not cross-table references or graph cycles. `createRelationships` derives associations; it does not impose foreign keys. The [archived isolated proof](https://github.com/juanibiapina/zero/blob/a7c78c39e8b82e1340bfc6956940a9d9fdc167d3/spikes/tinybase/README.md) already propagated a missing-Project Task through direct sync. TinyBase's `WsServerDurableObject` documents `onMessage` as a diagnostic hook and relays payloads to peers regardless of a store middleware rejection. The shipped design therefore retains invalid raw rows and derives a visible recovery projection instead of treating middleware as a domain admission boundary.

A **TinyBase-native workaround worth pursuing** was to retain Project deletion as a tombstone and derive a deterministic, visible recovery projection instead of requiring raw CRDT rows to obey foreign keys. The [archived local merge experiment](https://github.com/juanibiapina/zero/blob/a7c78c39e8b82e1340bfc6956940a9d9fdc167d3/spikes/tinybase/scripts/relation-projection-proof.ts) merged two disconnected replicas: one deleted a Project and its known Task, while the other created a late child. Both converged on the same tombstone and displayed the late Task as unfiled recovery; an arbitrary missing-Project Task was also visible. Two opposite After edges converged, with one accepted and the other reported as a cycle by stable-ID ordering. Later Worker and Pixel proofs covered linked Tasks, Waiting/After, recurring REST operations, terminal bootstrap, an offline Project/Task restart, complete import, and interrupted cutover. That projection is the shipped design.

**Accepted conflict policy (2026-09-25):** TinyBase keeps one value when two disconnected clients edit the same cell before seeing one another's write. The [archived same-cell experiment](https://github.com/juanibiapina/zero/blob/a7c78c39e8b82e1340bfc6956940a9d9fdc167d3/spikes/tinybase/scripts/same-cell-conflict-proof.ts) shows the losing value is absent after merge. The user accepts last-writer-wins for those concurrent same-field edits, including closely timed online races. This exception does **not** allow dropping queued actions, entire rows, or invalid relationships. Different-cell edits merge; Project deletion, After cycles, recurrence, and offline outbox migration retain their independent proof gates. The fixture uses direct cell edits; an application-level revision protocol is not part of the design.

## Evidence from this checkout

- `apps/agent-mobile/package.json` uses Expo SDK 57, TanStack DB 0.8.5, React Native 0.86.2, and `@op-engineering/op-sqlite`; it does not include any of these three libraries. `apps/agent-mobile/src/lib/db.ts` keeps the current persisted cache and offline outbox in separate SQLite files.
- `packages/agent-core/src/collection/base.ts` implements open-list snapshot reconciliation and a queued REST command executor. Mobile screens consume its TanStack collections/actions. Keeping a TanStack adapter limits screen churn, but the old cache/outbox must still migrate without losing pending actions.
- `apps/agent-api/src/UserDO/index.ts` keeps authoritative todo stores alongside unrelated agent state, uses `do-orm` transactions for some multi-row operations, and exposes per-user RPC methods to the existing HTTP routes. `apps/agent-api/src/store/tasks.ts` holds task domain operations, including recurrence. Existing task rows have no general sync revision or deletion marker; REST lists return open rows. Any library retaining this database must add a complete, ordered feed and deletion records for mobile pulls, including REST-originated writes.

| **Sync and conflicts** | [Replication](https://rxdb.info/replication.html) supplies checkpoints, retry and client conflict handling. The backend must implement pull, push (`assumedMasterState`, `newForkState`, return conflicting master state), and optional change notifications. **Default conflict handler discards the local fork**; test/implement a policy that does not silently lose offline edits. A thrown push error is retried, including permanent semantic errors, unless handled deliberately. | [MergeableStore](https://tinybase.org/guides/synchronization/using-a-mergeablestore/) has cell-level hybrid-logical-clock last-writer-wins behavior, so independent cell edits can merge. Materializers specify domain effects; their behavior under concurrent delete/recreate and recurrence needs tests. Existing `UserDO` tables and web REST commands will not appear in that store on their own. The Cloudflare adapter shows server-side clients, but does not convert existing `do-orm` writes to LiveStore events. |

Verify Clerk token on connection **and** per push. The docs warn that `syncPayload` can put tokens in URL parameters; use an appropriate header/transport and rotation policy. |

Native/DO integration and domain constraints are the main costs. | LiveStore Apache-2.0, currently [beta](https://docs.livestore.dev/evaluation/state-of-the-project/) with no 1.0 date; some storage-format upgrades rebuild local data. ## Additional candidates: Rocicorp Zero and Jazz

### Rocicorp Zero (`@rocicorp/zero` 1.9.0): reject for this goal

It now has [first-party Expo/React Native support](https://zero.rocicorp.dev/docs/react-native), including an `expo-sqlite` storage adapter (so an earlier native-support objection would be outdated). It is well suited to an *online* client/server app and can make existing Postgres writers visible through logical replication. But its [connection documentation](https://zero.rocicorp.dev/docs/connection#offline) explicitly says writes are **rejected** when disconnected, errored or awaiting auth; only already-synced reads work offline. Durable airplane-mode writes are a core product requirement. It also [requires Postgres 15+ with logical replication](https://zero.rocicorp.dev/docs/connecting-to-postgres) and a separately deployed [zero-cache process](https://zero.rocicorp.dev/docs/deployment). `UserDO` SQLite cannot serve as its upstream. Moving todos to Postgres would not fix the offline-write mismatch. Do not spike Rocicorp Zero for this refactor unless the offline-write requirement changes.

### Jazz: real candidate, but distinguish two generations

The [current Jazz 2 docs](https://jazz.tools/docs/install/client) describe a local-first relational database with an Expo/React Native adapter (`jazz-rn`), reactive queries, and Project-to-Task relations. [Writes commit locally while offline and sync after reconnect](https://jazz.tools/docs/concepts/how-sync-works/); independent column edits do not inherently replace an entire row. [Transactions](https://jazz.tools/docs/writing/transactions) include locally committed mergeable work and authority-checked exclusive work for invariants. A rejected exclusive transaction removes optimistic changes; the app must preserve recoverable user input and show the rejection. [Durability tiers](https://jazz.tools/docs/writing/writing-data#write-durability-tiers) distinguish local disk, edge, and global acknowledgment. [Row-level policies](https://jazz.tools/docs/auth/permissions) and [external JWT authentication](https://jazz.tools/docs/auth/authentication) can cover Clerk accounts; test issuer/audience and account mapping rather than assuming existing Clerk sessions automatically map to Jazz accounts.

Jazz 2 needs a **Jazz sync backend**, not a Durable Object binding over the current tables. The docs offer a hosted server or a [self-hosted persistent Rust process](https://jazz.tools/docs/getting-started/server-setup); Cloudflare Workers can act as server-side clients, not replace that core by importing the SDK. The web REST routes and any server todo writer would have to write to Jazz as the sole todo authority, while `UserDO` retains its unrelated agent data. That may be cleaner than changing the base class of the large `UserDO`, but it moves todo ownership and adds a hosted or separately operated backend. SDK 57 Android/Clerk/server-client behavior remains unproved here.

**Maturity:** `jazz-tools` currently publishes `0.20.19` as `latest` (classic Jazz) and `2.0.0-alpha.56` as `alpha`; the [Jazz 2 Expo guide](https://jazz.tools/docs/install/client) labels native support alpha and requires a matching development/release build, not Expo Go. [Classic Jazz](https://classic.jazz.tools/docs/react-native-expo) also supports Expo and [Clerk](https://classic.jazz.tools/docs/react-native-expo/key-features/authentication/clerk), but uses a different CoValue model. Do not adopt classic merely to avoid the Jazz 2 alpha without pricing the later migration between models. Classic [Cloud pricing](https://classic.jazz.tools/pricing) is not evidence of Jazz 2 pricing; get current Jazz 2 hosting terms or cost a self-hosted server before committing.

## What each library does *not* decide for us

1. **Data ownership:** RxDB can retain the `UserDO` database; TinyBase and LiveStore are attractive only if we accept a substantial change to how web/server todo writes reach the synced account state. None can safely infer existing REST mutations by watching a separate store automatically.
2. **Domain semantics:** Concurrent delete + late offline child creation, Project completion + After settlement, recurring completion/Undo, and invalid references are application rules. Library convergence is not a substitute for testing those rules. A rejected local edit must remain recoverable, whichever engine is chosen.
3. **Safe migration:** None reads and drains `zero-app-outbox-v2.sqlite` automatically. Never reset its schema/version to enable a new engine. Every engine needs a full initial seed (including terminal rows) from the existing account data and a crash-safe cutover.
4. **Server feed:** For RxDB, server rows must be deterministically ordered for checkpoint pulls and hard deletes must have durable tombstones (`_deleted` or mapped field). It is insufficient to point the client at `/api/tasks` or copy mobile's current outbox.

## Decision gates and next experiment

1. **TinyBase thin slice:** In an isolated branch, implement one authenticated Task and Project on SDK 57 Android, a DO `MergeableStore` with durable persistence, and one web REST writer that mutates the *same* store. No parallel `do-orm` todo authority. Prove offline process death, full terminal-row bootstrap, simultaneous independent/same-cell edits, concurrent delete+late child, After settlement, recurrence retry, recoverable blocked edits, account isolation, JSON persistence size/durability and the legacy-outbox migration path.
2. **Stop on a failed invariant:** If TinyBase cannot meet a proof, report which behavior failed and what change would be required. Do not start Jazz, LiveStore, Rocicorp Zero, RxDB or a custom client sync engine without a new design decision.

Do not ship a chosen engine until the two-device + web + offline-restart + interrupted-old-outbox migration tests pass. See `docs/plans/todo-local-replica-sync.md` for the product requirements and implementation order.
