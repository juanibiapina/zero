# Plan: Swap Tavily DEV key for a PRODUCTION key (research `read_page`)

Status: deferred by user decision 2026-07-23 — keeping the `tvly-dev-` key in prod for the free tier; execute this plan when moving to a production Tavily key.

## Goal

The research `read_page` tool (Tavily Extract) runs in prod on the user's DEV-tier key (`tvly-dev-...`, lower RPM). Replace it with a production Tavily key:
- Create a production Tavily key at app.tavily.com (this can be done via the browser using the `browse` skill if the user is logged in, OR the user pastes a key — the plan should support both; do NOT assume a key exists yet).
- Set `TAVILY_API_KEY` in ZeroVault project `zero-api` for BOTH `development` and `production` environments.
- Propagate: run `bin/fetch-secrets` (local) and `bin/sync-secrets-to-cloudflare` (worker).
- Verify: the worker secret is set, and a live Tavily Extract call returns 200 on the new key.

## Nature of this task

This is a **secrets/infra task, not a code change**. The key lives only in ZeroVault and Cloudflare; the repo never holds it. No repo edit is warranted and **no changelog entry** is needed: swapping the underlying API key changes no user-observable behavior (same tool, same responses, only higher rate limits). Confirmed nothing in the repo hardcodes a real key — the only `tvly-` strings are `tvly-secret` in `tavily.test.ts` (a test fixture) and doc placeholders. Do not print or commit the old or new key value.

## Findings

### Where the worker reads the key
- Env var name is exactly **`TAVILY_API_KEY`** (a Cloudflare Worker secret binding).
- Adapter: `apps/agent-api/src/pagefetch/tavily.ts` — `createTavilyFetcher(apiKey, options?)` POSTs to `https://api.tavily.com/extract` with header `Authorization: Bearer ${apiKey}`, body `{ urls, extract_depth: "basic", format: "markdown" }`. An unset key throws before any HTTP call.
- Wiring: `apps/agent-api/src/UserDO/index.ts:233` — `const fetcher = createTavilyFetcher(this.env.TAVILY_API_KEY);` passed into `orchestrateTurn`.
- Type decls: `apps/agent-api/worker-configuration.d.ts` already lists `TAVILY_API_KEY` in `Env` and `ProcessEnv`. Generated by `wrangler types`; no hand edit needed and no new declaration is required for a value-only swap.
- Docs: `docs/research.md` "Page fetch port" section describes the adapter; `docs/secrets.md` describes the ZeroVault flow.

### ZeroVault project / env
- Project **`zero-api`**, environments **`development`** and **`production`**. `development` generates `apps/agent-api/.dev.vars`; `production` is uploaded to Cloudflare Workers.
- CLI: run on demand via `pnpm dlx`. Note the version drift — `docs/secrets.md` shows `zerovault-cli@0.1.0`, but the bin scripts pin **`zerovault-cli@0.2.0`**. Use the version the scripts use (`0.2.0`) for consistency. The drift is harmless: `0.2.0` is verified to support every subcommand/flag this plan uses. Fixing `docs/secrets.md` to `0.2.0` is out of scope here.
- Requires env vars **`ZEROVAULT_API_KEY`** and **`ZEROVAULT_API_URL`** (`https://vault.apps.juanibiapina.dev`). Both are already present in this box's shell environment (verified), so ZeroVault operations are automatable here.

### The two propagation scripts
- `bin/fetch-secrets` — downloads all dev + web secrets from ZeroVault as JSON and serializes them to dotenv via `bin/json-to-dotenv.mjs`. For `zero-api`/`development` it regenerates `apps/agent-api/.dev.vars`, which is how the local worker picks up `TAVILY_API_KEY`. Requires `ZEROVAULT_API_KEY`/`ZEROVAULT_API_URL`.
- `bin/sync-secrets-to-cloudflare` — pushes prod secrets to Cloudflare via `wrangler secret bulk`. **Blast radius: the full script uploads to THREE live workers in one run** — `zero-api` (agent), `zerovault` (vault-api), and `zeroerrors` (errors-api) — not just the agent worker. Requires `ZEROVAULT_API_KEY`/`ZEROVAULT_API_URL` plus Cloudflare/wrangler auth. **This uploads to the live worker(s) immediately** — no deploy needed for a secret change; the running worker sees the new value. `secret bulk` merges (creates/updates keys in the payload, only deletes on explicit `null`), so re-pushing is idempotent and resets nothing — but if a vault/errors prod value in ZeroVault has drifted from what's live, the full script silently pushes those too. This plan scopes the change to just `zero-api` (see step 3) to avoid touching vault/errors.

### How Tavily Extract auth works (for verification)
Live 200 check (do NOT hardcode the key; read it from ZeroVault into a shell var):
```bash
curl -sS -o /dev/null -w "%{http_code}\n" https://api.tavily.com/extract \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"urls":"https://example.com","extract_depth":"basic","format":"markdown"}'
```

## Steps

### 1. Obtain the production key (two supported paths)

**Path A — user provides a key (preferred, simplest).** The user creates a production key at https://app.tavily.com and pastes it. No browser automation needed. Accept any non-dev key (a production key is not prefixed `tvly-dev-`).

**Path B — browser-create via the `browse` skill.** Only if the user has a logged-in Tavily session available to the browser tool. Load the `browse` skill, navigate to https://app.tavily.com, go to the API keys page, create a new **production** key, and copy its value **without printing it to the transcript** (copy to clipboard / a temp file the agent does not `cat`; do not screenshot or echo the key). If the browser is not authenticated to Tavily, stop and fall back to Path A — do not attempt to log in with the user's credentials.

> Account login / key creation is the one part that may need the user. If the browser has no Tavily session, the user must either log in for Path B or hand over a key for Path A. Everything after this step is automatable on this box.

Sanity-check the obtained key with the live curl above before storing it (expect `200`), reading it from a non-echoed shell var (see step 2), never inline. **Never echo, `cat`, or log the key value in any step. Do not run any of these steps under `set -x`.**

### 2. Store in ZeroVault `zero-api` (dev + prod)

**Read the key into a non-echoed shell var; reference it only as `"$KEY"`.** `secrets set` has no stdin path, so the value must reach it as an argument — but via the variable, so shell history and the transcript store the literal `"$KEY"`, not the secret.

```bash
# (Optional rollback capture, see below) save the current prod value first:
OLD_KEY=$(pnpm dlx zerovault-cli@0.2.0 secrets get TAVILY_API_KEY -p zero-api -e production)

read -rs KEY; echo            # paste key, input hidden; or: KEY=$(cat /path/to/keyfile)
pnpm dlx zerovault-cli@0.2.0 secrets set "TAVILY_API_KEY=$KEY" -p zero-api -e development
pnpm dlx zerovault-cli@0.2.0 secrets set "TAVILY_API_KEY=$KEY" -p zero-api -e production
unset KEY
```
Set the **same** production key in both environments (dev and prod worker runtime both benefit from the higher RPM). Confirm with `secrets list -p zero-api -e development` and `-e production` (values masked — the list never prints values).

**Rollback.** Before overwriting, capture the current prod value into `OLD_KEY` (above); it is held in the shell var only, never printed. If the new key fails verification, restore with `secrets set "TAVILY_API_KEY=$OLD_KEY" ...` for both envs and re-run the sync, then `unset OLD_KEY`. (The current value is a `tvly-dev-` key; if not captured, a fresh dev key can be re-created at app.tavily.com as a fallback.)

### 3. Propagate

```bash
bin/fetch-secrets                 # regenerates apps/agent-api/.dev.vars (local dev picks up new key)
```

For the Cloudflare push, **scope to the agent worker only** — do not run the full `bin/sync-secrets-to-cloudflare`, which also pushes to the vault and errors prod workers (see Findings). Run just the `zero-api` block:

```bash
pnpm dlx zerovault-cli@0.2.0 secrets download -p zero-api -e production --format json \
  | pnpm --dir apps/agent-api exec wrangler secret bulk
```

This uploads `zero-api`/`production` secrets to the live agent worker via `wrangler secret bulk`. If you instead run the full `bin/sync-secrets-to-cloudflare`, know that it re-pushes vault + errors prod secrets to their live workers too; confirm those ZeroVault projects are in sync with live first. `secret bulk` merges and resets nothing, so re-pushing existing secrets is safe.

### 4. Verify

1. **Worker secret present (presence only, not value).** Confirm the binding exists:
   ```bash
   pnpm --dir apps/agent-api exec wrangler secret list
   ```
   `TAVILY_API_KEY` should appear. **Caveat:** `wrangler secret list` prints names only. The key name already existed, so this output is byte-identical before and after the swap — it proves the binding is present, **not** that the value changed. Do not read it as evidence the new value is live.
2. **Live Tavily Extract 200 on the new key (REQUIRED).** Read the stored prod key back from ZeroVault into a non-echoed shell var and run the curl from Findings; expect HTTP `200`. This proves the new key value is valid at Tavily.
   ```bash
   KEY=$(pnpm dlx zerovault-cli@0.2.0 secrets get TAVILY_API_KEY -p zero-api -e production)
   curl -sS -o /dev/null -w "%{http_code}\n" https://api.tavily.com/extract \
     -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
     -d '{"urls":"https://example.com","extract_depth":"basic","format":"markdown"}'
   unset KEY
   ```
3. **Local `.dev.vars` updated.** Grep-confirm the var is present (not the value) in `apps/agent-api/.dev.vars`.
4. **Prod `read_page` round trip (REQUIRED — the only direct proof of the swap).** `secret list` can't show the value changed and the step-2 curl proves the key is valid, not that the *running worker* uses it. Exercise the tool end to end: prompt the prod agent to research a URL (or run against the local dev worker after `bin/fetch-secrets`), confirming a page is fetched without a rate-limit error. This round trip through the live worker is the only direct evidence the new key is the one in effect. Equivalent acceptable substitute: a live Tavily Extract `200` issued with the NEW key value directly (step 2) **plus** confirmation the bulk upload succeeded — but the `read_page` round trip is preferred.

## Automatable here vs needs the user

- **Automatable on this box** (ZeroVault creds present, wrangler auth assumed): steps 2, 3, 4, and Path B of step 1 *if* the browser already has a Tavily session.
- **Needs the user:** creating the production key — either by pasting one (Path A) or by having a logged-in Tavily browser session (Path B). Nothing else.

## Acceptance criteria

- `TAVILY_API_KEY` in ZeroVault `zero-api` (both `development` and `production`) holds a non-dev (production) Tavily key.
- `wrangler secret list` for the agent worker shows `TAVILY_API_KEY` — confirming the binding is **present** (list shows names only; it does not and cannot prove the value swapped).
- A live Tavily Extract call with the new key value returns HTTP `200`.
- A prod `read_page` round trip through the live agent (or local worker after `fetch-secrets`) fetches a page without a rate-limit error — the direct proof the new key is in effect.
- `apps/agent-api/.dev.vars` regenerated with the new key.
- Cloudflare push scoped to the `zero-api` agent worker (vault/errors prod workers untouched).
- No key value written to the repo, git history, logs, or the transcript.
- No repo code change and no changelog entry (not user-observable — same tool, same responses; only users hitting the dev-tier ceiling would see higher limits, so the entry is reasonably skipped).
