# Compact mobile snackbars

## Goal

Make every existing mobile snackbar a compact, normally one-line result with only useful copy and reachable actions. The current Home screenshot shows a roughly 200dp-high card for “Completed”, a project name, Undo, and “Waiting for…”. Completion, project creation, filing/moving tasks, and project failures must use the same compact visual treatment. At ordinary phone width and font scale, target a single row about one 48–56dp touch target tall. At large font scales or very narrow widths, allow height to grow rather than hide an action or essential error text.

This is a mobile change, not a new notification system. Completion must still write immediately; Undo must still work. Keep the existing four-second base lifetime, Android accessibility-recommended extensions, sticky project failures, swipe dismissal, activity/route dismissal, and FAB/tab/safe-area clearance.

## Current state and decision

- `apps/agent-mobile/src/components/toaster.tsx` is the single root-mounted renderer adapter. It renders a title, optional description, and a **separate wrapping action row** inside a padded, raised card. That layout, rather than the shared timer, creates the height in the screenshot.
- `packages/agent-core/src/toast/controller.ts` owns the headless observable toast interface, replacement by id, and timers. `undoableAction` in that package owns the shared `undo` id. The web app has its own renderer in `apps/agent-web/src/components/Toaster.tsx`. Keep their interfaces and web appearance unchanged: the mobile renderer is the seam for visual behavior.
- Mobile producers are `src/components/task-detail.tsx` (task completion, including project context and Waiting), `src/app/(signed-in)/projects/[id].tsx` (project completion and late failures), `src/components/quick-add-composer.tsx` (project creation), and `src/lib/task-feedback.ts` (filing/moving). Recent changes deliberately removed success snackbars for ordinary add/schedule/postpone actions; do not reintroduce them.
- Retain the existing renderer rather than replace it with a new library or redesign the shared controller. A separate snackbar abstraction would duplicate a working seam; native replacement would risk the existing animation/gesture, route, and accessibility behavior. Use the app's Uniwind tokens in `global.css` and existing `Text` styles rather than a new palette.

## Implementation

1. **One row for every current toast shape.** In the mobile `ToastRow`, lay out one bounded text region and a trailing group of actions on the same horizontal row. Merge `message` and an optional short `description` into one visible phrase; do not stack a caption or reserve a second action row. Keep a compact surface, restrained radius/elevation, and horizontal padding from existing tokens. Use `minWidth: 0`/flex shrink on the text, not on actions; retain 48dp touch targets for pressable text and buttons. Keep the current FAB offset, enter/exit animation, and horizontal swipe. A project `descriptionAction` should make the combined result/project text a visibly interactive, accessible 48dp target; a press still navigates and dismisses. All current `action`, `secondaryAction`, and `link` callbacks remain distinct trailing controls in their existing order. The existing project-task case has two trailing buttons, Undo and Waiting; do not silently drop either or the project link. If an unforeseen combination cannot fit, let it wrap instead of clipping a control. Check that a single-line 48–56dp row does not overlap the FAB or tabs on Home, Upcoming, and Projects.
2. **Short, specific copy at each mobile producer.** Remove generic directions such as “Find it on Home” and repeated project names where the current screen already supplies context. Keep one succinct outcome per case: task completed (including recurring completion forever), project completed, project created, task filed/moved/removed, and project write/refetch failure. Keep `View` for a destination/project creation, `Undo` for completion, and a short visible Waiting action with a full accessibility label. For a project-linked completion, retain the project name as the tappable inline context, not a second line. For future-dated filing, the visible copy must still make “Upcoming” intelligible if `View` opens Upcoming; do not claim it opens the project. Shorten `reportProjectFailure` to a diagnosis plus a useful recovery cue; distinguish a failed write from a successful write whose list refresh failed. Keep an explicit, accessible Dismiss control for sticky failures. Do not replace important recovery instructions with an ellipsis or hide them only in a screen-reader announcement. Set concise copy in mobile producers, not by string-matching in the renderer. Reuse the existing toast fields/callbacks; change shared types only if a real new need is demonstrated.
3. **Small screens and accessibility are intentional exceptions to the one-line target.** At normal font scale, one line with an ellipsized *project title* is acceptable when actions need the space; the full title stays in the accessibility label and announcement. Essential result/error text and actions must remain readable at large font scales: allow text or the action group to wrap when required instead of forcing fixed height or shrinking fonts. Keep `AccessibilityInfo.announceForAccessibility` meaningful for optional context and errors, Android recommended timeout, semantic button labels, and dark/light contrast. Make the inline project target visibly identifiable as a link without adding another button. Do not add an ornamental success icon or a second status line.
4. **Verify every variant through its public interface.** Update `src/components/__tests__/toaster.test.tsx` to assert one row and working controls for: plain feedback; Undo only; project completion context + Undo + Waiting and tappable project; creation/destination + View; sticky error + Dismiss. Test long project names/narrow layout and large-text fallback without relying on brittle pixel snapshots. Update the existing screen/producer tests in `src/app/(signed-in)/__tests__/` and `src/lib/__tests__/task-feedback.test.ts` for revised copy, links, persistence/Undo, and failure-vs-refresh messages. Preserve the timing, swipe, route, and replacement tests. Extend the existing `.maestro/hermetic/02-save-project-description.yaml` flow for native rendering: complete a project task, confirm compact snackbar and Undo/Waiting remain tappable, and cover a View/error case where feasible without changing the harness's one-open-task postcondition. Use device screenshots/artifacts for the visual height and contrast judgment that tests cannot assert.
5. **Keep product records aligned.** Add one most-recent-first `- YYYY-MM-DD: ...` user-perspective entry to `apps/agent-mobile/CHANGELOG.md` **in the same code change**; load the `changelog` skill before editing it. Update `docs/todo-app.md` only where its living description of snackbar content/actions would become inaccurate. Do not rewrite historical plans or put the entry in the agent or root changelogs.

## Out of scope

Web snackbar styling, shared queue/timer semantics, server writes, scheduling feedback policy, and redesigning the add drawer or project screen. Do not remove Undo, Waiting, project navigation, or error recovery merely to force a row onto a small screen.

## Verification

Stop Metro and local Gradle first; run `gob run bin/ci` per repository convention. On this host, whole-repo CI can stop when host `workerd` fails (NixOS EPIPE); report that limit and separately run mobile Jest in band, lint, typecheck, and an Android Expo export. For native layout/gesture proof run `pnpm --filter @zero/agent-mobile e2e:pixel` and check the harness's storage/cleanup assertions. Assess the screenshot at regular and enlarged Android text, in light and dark themes, for one-row normal cases and readable fallbacks.

## Skills for implementation

- `expo-overview`, `expo-native-ui`, `expo-ui` — respect SDK 57 and native snackbar/touch/accessibility expectations before changing the renderer.
- `impeccable` (distill) — remove redundant visual hierarchy and copy without hiding functionality.
- `testing` — test observable toast actions and lifetime through the renderer and producer interfaces.
- `changelog`, `documentation` — write the mobile entry and update only the living product record.
- `reproducible-locally` — use the hermetic Pixel flow for native proof.

## Acceptance criteria

All current mobile toast producers show a normally single-row, compact snackbar on a standard phone. No optional description forms a second visual line in that normal case. Undo, Waiting, View, project navigation, Dismiss, swipe, and the accessibility-adjusted lifetime still work. No important error or control is lost on narrow screens or large text. No web visual change or new ordinary success toast ships; tests, the Pixel flow, and the mobile changelog land together.
