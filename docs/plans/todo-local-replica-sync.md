# Complete local todo data with library-led sync

## Conclusion

Make the mobile todo app local-first: every Task, Project, manual Waiting condition, and After relationship used by the app lives durably on the device, including completed, Done, and resolved records. The app reads and writes locally; an account synchronizes that data across devices. **Use TinyBase's MergeableStore, Expo persistence, and Cloudflare Durable Object synchronizer; prove the integration before rollout.** Keep sign-in required while building and verifying this foundation. Optional login, device-only free use, and sign-out choices follow later on the same local data model—there is no separate guest role or guest store.

Do not reintroduce “last server-accepted write wins,” a custom cursor journal, or prescribed HTTP error codes. Those were provisional interview ideas, not product requirements. Use TinyBase's merge behavior and prove deletion, retry, account isolation, and domain transitions under the scenarios below. Complete the redesign before inviting testers; a clock deadline does not substitute for migration proof.

## Why a redesign is necessary

`docs/storage.md` describes today's mobile SQLite as a **disposable cache** with a separate durable outbox. `packages/agent-core/src/collection/base.ts` fetches each server entity's *open* working set and removes locally cached rows absent from that response. `ENTITY_CACHE_VERSION` can reset that cache. Server `DbTaskStore`, `DbProjectStore`, and `DbWaitingConditionStore` retain completed/Done/resolved rows, but `/api/{tasks,projects,waits}` return only the open rows. The in-memory fallback cannot guarantee offline durability. Thus the current stack does not provide a complete local replica even when signed in.

The app already has client-minted UUIDs, domain verbs, TanStack DB live queries, op-sqlite, and a durable offline outbox. Keep existing screen behavior and reuse the domain derivations where the selected library permits. A new sync engine must also account for writes through the web REST routes and `UserDO` coordination: Project deletion cascades to its Tasks and relationships; Project completion settles After rows; recurring Task completion advances a cursor. Today's Task-create route validates `projectId` as a UUID but not as an existing Project, so a delayed offline add can create an invisible orphan. The redesign must prevent silent loss or hidden orphaned work without assuming the repair must be a particular HTTP response.

## Product requirements (not a sync-algorithm prescription)

1. **Offline ownership:** After the first authenticated load, all todo rows relevant to the mobile app remain on-device, including terminal rows. Actions commit durably before the app reports success. Cold start, airplane mode, reconnect and lost acknowledgements must not lose local work. A storage failure is visible; the mobile path cannot silently degrade to memory-only or online-only writes.
2. **Convergence:** Two devices eventually show compatible todo state after disconnected edits and reconnection. Test independent edits, same-field edits, completion/Undo, recurrence, reorder, Project deletion and late child creation. TinyBase's `MergeableStore` merges cells using hybrid-logical-clock ordering; document the actual same-cell, independent-cell, and deletion outcomes with concrete tests. No local change may vanish silently because an older remote snapshot replaced it.
3. **Domain integrity:** Task/Project membership and Waiting/After relationships remain valid. Project completion/deletion and recurrence keep their existing user-visible semantics. A concurrent deletion and offline edit must have an explicit tested outcome that does not leave hidden orphaned work. If the library rejects or cannot merge a change, retain it recoverably and show a sync issue; do not retry permanently invalid changes forever.
4. **Account and web compatibility:** Authenticated users only see their account's data. Existing web writes must reach mobile, and mobile changes must appear on web. There is **one account source of truth**, not an event store and a `UserDO` table set that can diverge. Migrate the web/server todo write path to the TinyBase authority; never silently dual-write to the old tables.
5. **UI scope:** Keep Home, Projects, Project detail, and Browse/Upcoming showing their present open subsets, plus launcher count, Undo, day rollover, and manual emoji picker. Retaining terminal rows locally does not require a history screen or a search UI now; it makes future local search possible. AI icon suggestions remain a network/auth-dependent feature.

## TinyBase integration gate

TinyBase is the chosen library; the [candidate evaluation](../investigations/todo-sync-libraries.md) records why. Use its `MergeableStore`, Expo SQLite persister in JSON mode, and Cloudflare DO WebSocket synchronizer, subject to a real SDK 57 Android proof. Do not introduce another todo authority: the existing web REST routes and server writers must mutate the same per-user TinyBase account data. The chosen server location is a separate per-account `TaskDO` in the same Worker; the [first vertical slice](todo-local-replica-task-do-slice1.md) records where data lives at each stage. It must not be dual-written with `UserDO`. Prove authenticated routing, durable offline restart, complete initial import, Project/Task/After integrity, recurrence, concurrent deletions, and legacy-outbox migration before changing production reads. Do not add a custom protocol or quietly switch to Jazz without a new decision.

The [isolated proof](../../spikes/tinybase/README.md) passed Worker/REST/client transport and Android offline-edit restart/reconnect checks. It also demonstrated an invalid Task/Project reference propagating over direct WebSocket sync despite REST validation. This is a **failed domain-integrity gate**, not permission to switch the production path. The proof does not yet establish Clerk routing, existing `UserDO`/web writers, dependent-row semantics, or migration safety.

## Small deliverables

Each deliverable has an observable exit test. Keep real accounts on the existing path until their explicit cutover. Fixture-only code must not write a second live copy of any account's todos. A passing transport proof does not waive the domain-integrity gate.

0. **Isolated proof (done, not a production integration).** [Worker, REST, Node clients and Pixel results](../../spikes/tinybase/README.md) establish offline SQLite persistence and bidirectional transport. Direct WebSocket sync also created an orphan Task. This is the first blocker to resolve.
1. **A loose Task crosses the real app and Worker for a fixture account.** [Slice 1](todo-local-replica-task-do-slice1.md) connects the mobile Home path, durable Expo SQLite, authenticated test-only WebSocket sync, `TaskDO` SQLite, and the existing web Task REST route. A force-stopped phone restores an offline edit and sees a REST edit; real accounts still use `UserDO`. The slice document is the target data-location map. Direct-sync relationship integrity remains unproved.
2. **The sync trust and relationship-integrity gate passes.** With the real TinyBase synchronizer, prove how invalid direct edits, late offline children after Project deletion, and same-cell/deletion conflicts avoid hidden or silently lost work. REST-only validation is insufficient. Preserve blocked changes recoverably; stop and request a design decision if this cannot be done without a bespoke sync protocol.
3. **A Project and its Task cross both surfaces.** Add a real Project relationship to the fixture account's `TaskDO`, mobile Project screen, and existing web REST routes. A Project created on one device and a Task added offline on another converge; concurrent deletion follows the tested recovery rule. Keep production accounts on the old path until all todo entities can switch together.
4. **The fixture account supports the complete todo model.** Add manual Waiting, After, terminal rows, Project completion/deletion, Task recurrence and Undo to the same store and signed-in screens. Two devices and REST converge after offline restart and retry; recurring completion advances once.
5. **Existing server accounts have a safe cutover path.** Build an idempotent, auditable complete import of open and terminal rows from `UserDO` to `TaskDO`, then a per-account write fence/handoff so REST, web and any server todo writer use **only** the new store after that account switches. A dark import must not be exposed as an active second authority. Keep legacy REST contracts usable for old mobile builds and pending outbox requests. Exit: interrupted/retried handoff loses no writes, and old todo tables are no longer writable for switched accounts; rollback and account deletion are proven. Do not depend on a cross-DO transaction that Cloudflare does not provide.
6. **Existing mobile installs cross without lost local work.** Read and drain or losslessly translate `zero-app-outbox-v2.sqlite` and switch the signed-in mobile data module only when that account has a complete synced dataset. An offline or interrupted install stays on its existing path until safe; old files remain available for retry. Filter terminal rows in the current screens without deleting them locally. Exit: force-stop at each migration boundary preserves queued actions, offline writes, UI behavior and account separation in a hermetic Pixel flow.
7. **Release gate (part of the shipping change).** Run two-device, web REST, server-writer, offline restart, account-deletion, domain-conflict, size/latency and rollback checks. Update `docs/storage.md` as the storage source of truth, `docs/todo-app.md`, relevant entity docs, the mobile README, and a same-change user-facing entry in `apps/agent-mobile/CHANGELOG.md` (load the `changelog` skill first). Keep sign-in required; optional sign-in and sign-out choices remain later work. No tester invitation precedes these checks.

## Proof and stop conditions

Test the chosen library's actual interface through two independent clients and the existing web routes. Include fully offline cold start, pending local edit over incoming remote data, completion/Undo across restart, terminal record bootstrap, Project deletion with an offline child Task, After settlement/restore, recurring completion retries, same-field concurrency, invalid relationship handling, lost acknowledgement, and server-originated changes. Add behavior-named `.maestro/hermetic/` flows using isolated SQLite files and the local Worker; never clear production device stores or Clerk sessions. Test a standalone build's native persistence path as well as the Pixel development client.

Run `gob run bin/ci`; on the documented NixOS `workerd` failure, run touched-package tests, lint, typecheck, Android export, and `pnpm --filter @zero/agent-mobile e2e:pixel` separately. Stop Metro/Gradle before checks on the small host. **Stop the rollout** if a local action is not durable, web/server writes bypass the chosen authority, domain transitions diverge, or the existing outbox cannot be migrated without data loss. Test rollback before shipping.

## Later: optional sign-in, not a separate guest product

Once signed-in local-first sync works, unauthenticated use runs the same local data module with synchronization paused. On sign-out the user chooses **Remove items from this device** (safer default) or **Keep items on this device** (warn that anyone with access to the phone can read them). Keep permits continued offline work and later sync with **any** account. A different account needs an explicit internal merge/seed of already-synced local data—its checkpoint cannot just be reused. Do not expose the previous account's private data accidentally during that transition. Sign-out must not discard unsynced work; replace Clerk's native `UserButton` with an app-owned account screen before offering a guarded sign-out action. Optional login, payments, history/search UI, web offline support, and a public free tier remain out of scope for the sync redesign.
